## 🎯 核心概念

### 1. 代数（Generation）

从推荐人向下计算的层级数：
- **第1代**：我直接推荐的人
- **第2代**：我推荐的人推荐的人
- **第N代**：依此类推

```
          我（推荐人）
           ├─ A（第1代，直推）
           │   ├─ A1（第2代）
           │   └─ A2（第2代）
           └─ B（第1代，直推）
               └─ B1（第2代）
```

### 2. 职级（Rank）

基于业绩、团队规模等指标的等级系统：
- **普通会员** → **VIP** → **经理** → **总监** → **合伙人**

不同职级享有不同的奖励比例和权限。

### 3. 业绩类型

- **个人业绩**：用户自己的订单金额
- **直推业绩**：第1代的订单金额总和
- **团队业绩**：整个团队（所有代数）的订单金额总和

## 🥇 1. 级差奖（Differential Bonus）

### 📌 核心思想

级差奖是MLM中最经典的奖励机制之一，基于**职级差异**进行分润。核心理念是：**职级越高，能拿的比例越大**。它不关心你和下单人隔了几代，只看双方的职级差。

### 🎯 适用场景

- ✅ 传统直销行业（安利、康宝莱等）
- ✅ 保险代理系统
- ✅ 需要强调职级晋升的业务
- ✅ 团队深度较深的组织架构

### 📐 计算公式

```
级差奖 = 订单金额 × (自己职级比例 - 下单人职级比例)
```

**关键点**：
- 如果下单人职级 ≥ 自己职级 → 无级差奖
- 只向上发放到第一个更高职级为止
- 每个职级只拿一次级差

### 📊 完整示例

**层级结构**：
```
张三 (总监, 15%) 
  └─ 李四 (经理, 10%) 
       └─ 王五 (VIP, 5%) 
            └─ 赵六 (会员, 0%) 
```

**赵六下单 1000元，各级分润**：
- 王五级差奖：1000 × (5% - 0%) = **50元**
- 李四级差奖：1000 × (10% - 5%) = **50元**
- 张三级差奖：1000 × (15% - 10%) = **50元**
- **总计发放**：150元

**如果李四是总监(15%)**：
```
张三 (总监, 15%) 
  └─ 李四 (总监, 15%)  ← 同级，张三无级差
       └─ 王五 (VIP, 5%)
```
- 王五下单1000元
- 李四拿：1000 × (15% - 5%) = **150元**
- 张三拿：**0元**（同职级无级差）

### ⚠️ 常见陷阱

1. **压级问题**：高职级故意不培养下级晋升，保持级差
   - **解决方案**：配合"平级奖"激励培养
   
2. **断代问题**：中间某层离职，导致链路断裂
   - **解决方案**：设置"滑落机制"或"平推规则"
   
3. **职级倒挂**：新人直接空降高职级
   - **解决方案**：严格晋升条件，设置保护期

### 💡 最佳实践

- **职级比例差不宜过大**：建议每级相差3-5%
- **设置封顶机制**：单笔订单级差奖不超过N元
- **配合团队业绩考核**：避免只顾个人不管团队
- **透明的职级晋升规则**：让所有人看到晋升路径

### 🆚 与推荐奖的区别

| 对比项 | 级差奖 | 推荐奖 |
|-------|--------|--------|
| 发放层级 | 全链路（直到职级相等） | 仅直接推荐人 |
| 金额计算 | 基于职级差 | 固定比例 |
| 依赖关系 | 职级体系 | 推荐关系 |
| 典型场景 | 传统直销 | 电商分销 |

### 📈 实战优化建议

**场景1：新用户激活**
- 问题：新用户职级低，上级拿的级差少
- 方案：首单给予额外的"启动奖"

**场景2：大客户订单**
- 问题：大单导致级差奖过高
- 方案：设置单笔封顶或采用阶梯比例

**场景3：团队停滞**
- 问题：高层躺赚，不培养新人
- 方案：引入"活跃度考核"，不活跃则级差减半

## 🥈 2. 推荐奖/直推奖（Referral Bonus）

### 📌 核心思想

推荐奖是所有分销系统的**基础奖励**，简单直接：**谁推荐的人下单，谁就拿奖**。它强调的是"第一次触达"的价值，是最容易理解、最广泛应用的奖励机制。

### 🎯 适用场景

- ✅ 电商分销系统（淘宝客、拼多多等）
- ✅ SaaS推荐计划（Dropbox、Notion等）
- ✅ 教育培训机构
- ✅ 所有需要拉新的业务

### 📐 计算公式

```
推荐奖 = 订单金额 × 固定比例
或
推荐奖 = 固定金额/单
```

**两种模式**：

1. **百分比模式**：适合客单价不固定的场景
   ```
   订单1000元 × 10% = 100元
   订单5000元 × 10% = 500元
   ```

2. **固定金额模式**：适合标准化产品
   ```
   每成交1单 = 50元
   无论订单大小
   ```

### 📊 完整示例

**场景1：电商分销**
```
张三（分销员） → 推荐码ABC123
  └─ 李四（新用户，使用ABC123注册）
       └─ 首单购买 1000元

推荐奖规则：首单10%，复购5%
张三推荐奖：1000 × 10% = 100元
```

**场景2：分级比例**
```
不同职级享受不同推荐比例：
- 普通会员：5%
- VIP会员：8%
- 代理商：10%

张三（VIP） → 推荐李四
李四下单1000元
张三推荐奖：1000 × 8% = 80元
```

**场景3：阶梯奖励**
```
累计推荐业绩达标后提高比例：
- 0-1万：5%
- 1-5万：8%
- 5万+：10%

张三累计推荐业绩 3万，本月李四下单5000元
推荐奖：5000 × 8% = 400元
```

### ⚠️ 常见陷阱

1. **虚假推荐**：刷单、自己推荐自己
   - **解决方案**：
     - 绑定手机号/身份证，防止重复注册
     - 首单需实名认证
     - 设置推荐冷静期（注册后N天内的订单不计奖）

2. **比例设置过高**：导致利润空间被压缩
   - **解决方案**：
     - 精确计算成本和毛利
     - 首单可以高比例引流，复购降低
     - 设置单笔封顶金额

3. **无限期有效**：多年前推荐的客户持续产生佣金
   - **解决方案**：
     - 设置有效期（如推荐关系1年后失效）
     - 引入"活跃度"概念，不活跃则降低比例
     - 客户可以更换推荐人

### 💡 最佳实践

#### 1️⃣ 首单激励策略
```
首单：15%  （吸引推广）
复购：8%   （维持收益）
3次购买后：5% （长期绑定）
```

#### 2️⃣ 双向激励
```
推荐人：获得100元
被推荐人：获得50元优惠券
→ 双赢，提高转化率
```

#### 3️⃣ 时效性激励
```
前100名推荐成功：额外奖励200元
本月推荐满10人：晋级资格
→ 制造紧迫感
```

#### 4️⃣ 品类差异化
```
标准商品：10%
高利润商品：15%
清仓商品：5%
→ 引导推广方向
```

### 🆚 推荐奖 vs 越级奖

| 对比维度 | 推荐奖 | 越级奖 |
|---------|--------|--------|
| **发放对象** | 仅直接推荐人 | 第2代及以后 |
| **奖励金额** | 较高（10-20%） | 递减（5%、3%、2%...） |
| **依赖深度** | 不依赖 | 强依赖团队深度 |
| **激励方向** | 拉新 | 团队裂变 |
| **计算复杂度** | 简单 | 需要递归计算 |

### 📈 实战数据参考

**行业标准比例**（仅供参考）：

| 行业类型 | 典型比例 | 备注 |
|---------|---------|------|
| 虚拟产品（课程、软件） | 20-50% | 零边际成本 |
| 实物电商 | 5-15% | 需考虑物流成本 |
| 高客单价（房产、汽车） | 0.5-2% | 绝对金额大 |
| 订阅制（月付） | 首月100%，后续10% | 获客成本前置 |
| 金融产品 | 首年保费的50-100% | 监管限制多 |

### 🔧 技术实现要点

```go
// 1. 推荐关系绑定
type User struct {
    ID        string
    SponsorID string  // 推荐人ID
    BindTime  time.Time
}

// 2. 防作弊检查
func IsValidReferral(user, sponsor User) bool {
    // 不能自己推荐自己
    if user.ID == sponsor.ID {
        return false
    }
    // 不能是同一设备/IP
    if user.DeviceID == sponsor.DeviceID {
        return false
    }
    // 推荐关系是否在有效期内
    if time.Since(user.BindTime) > 365*24*time.Hour {
        return false
    }
    return true
}

// 3. 比例动态计算
func GetReferralRate(sponsor User, order Order) float64 {
    rate := 0.10  // 默认10%
    
    // 首单加成
    if order.IsFirstOrder {
        rate = 0.15
    }
    
    // 职级加成
    if sponsor.Rank == "VIP" {
        rate += 0.03
    }
    
    // 封顶检查
    maxBonus := order.Amount * 0.20
    return min(rate, maxBonus/order.Amount)
}
```

### 🎓 案例学习

**案例1：拼多多的"砍一刀"**
- 不是传统推荐奖，而是"助力"机制
- 降低了用户心理门槛（帮朋友，不是推销）
- 病毒式传播效果好

**案例2：瑞幸咖啡**
- "分享得券"：推荐人和被推荐人各得1杯
- 低成本（咖啡成本低）
- 高频消费，复购率高

**案例3：某SaaS产品**
- 首月付费100%给推荐人
- 后续月付费10%持续返佣
- LTV（客户生命周期价值）模型

## 🥉 3. 越级奖/代数奖（Override Bonus）

### 📌 核心思想

越级奖是**推荐奖的延伸**，从第2代开始按代数递减发放。它的核心理念是：**奖励团队深度**，让每个人都有动力去培养下级的下级，形成多层级的裂变网络。

### 🎯 适用场景

- ✅ 需要快速裂变的社交电商
- ✅ 保险行业的团队组织
- ✅ 教育培训的代理体系
- ✅ 任何希望鼓励"深度发展"的业务

### 📐 计算公式

```
越级奖 = 订单金额 × 代数对应比例

典型代数比例：
第1代：10%（推荐奖）
第2代：5%（越级奖开始）
第3代：3%
第4代：2%
第5代：1%
```

### 📊 完整示例

**场景1：标准越级奖**
```
张三（发起人）
  └─ A（第1代，张三直推）
       └─ B（第2代）
            └─ C（第3代）
                 └─ D（第4代）

D下单1000元，各级分润：
- C拿推荐奖（第1代）：1000 × 10% = 100元
- B拿越级奖（第2代）：1000 × 5% = 50元
- A拿越级奖（第3代）：1000 × 3% = 30元
- 张三拿越级奖（第4代）：1000 × 2% = 20元

总计：200元
```

**场景2：职级加成的越级奖**
```
基础比例 + 职级加成：

张三（总监，+2%加成）
  └─ A（经理，+1%加成）
       └─ B（普通会员）
            └─ C（普通会员）

C下单1000元：
- B：1000 × 10% = 100元
- A：1000 × (5% + 1%) = 60元（越级+职级）
- 张三：1000 × (3% + 2%) = 50元

职级越高，越级奖越多
```

**场景3：分段比例**
```
客单价不同，比例不同：

订单金额 < 500元：
- 第2代：5%
- 第3代：3%

订单金额 ≥ 500元：
- 第2代：3%（降低，防止大单压力）
- 第3代：2%

C（第3代）下单2000元：
张三越级奖 = 2000 × 2% = 40元
```

### ⚠️ 常见陷阱

1. **代数过深导致利润被吃光**
   - ❌ 错误：第1-10代都发奖，比例相加超过50%
   - ✅ 正确：严格控制在5代内，总比例不超过25%
   
2. **高层躺赚问题**
   - 问题：早期加入者躺着收底层的越级奖
   - 解决：
     - 设置"活跃度要求"：每月必须有直推业绩
     - 引入"滑落机制"：不活跃则不享受深层越级奖
     - 代数随职级动态变化：普通会员只拿2代，总监才能拿5代

3. **计算复杂度爆炸**
   - 问题：用户量大时，每个订单需要递归查询多层上级
   - 解决：
     - 数据库设计：预存储每个用户的上级链路（JSON或关联表）
     - 缓存机制：热点用户的上级关系缓存
     - 异步计算：奖金不实时到账，每日批量结算

### 💡 最佳实践

#### 1️⃣ 代数比例设计原则

```
递减原则：每代比例应显著递减
第1代：10%
第2代：5%（减半）
第3代：2.5%（继续减半）
第4代：1%
第5代：0.5%

总计：19%（控制在成本可承受范围）
```

#### 2️⃣ 动态代数限制

```go
// 根据职级决定能拿几代
func GetMaxGeneration(rank string) int {
    switch rank {
    case "会员":
        return 1  // 只拿直推，无越级
    case "VIP":
        return 2  // 可拿到第2代
    case "经理":
        return 3
    case "总监":
        return 5
    default:
        return 1
    }
}
```

#### 3️⃣ 防作弊机制

```go
// 检测异常深度
func DetectAbnormalDepth(user User) bool {
    // 如果某个用户的下级超过10代，可能有问题
    depth := CalculateMaxDepth(user.ID)
    if depth > 10 {
        AlertRiskTeam(user.ID, "异常深度")
        return true
    }
    
    // 检测单链问题（每代只有1个人）
    if IsSingleChain(user.ID) && depth > 5 {
        AlertRiskTeam(user.ID, "疑似虚假发展")
        return true
    }
    
    return false
}
```

```go
    UserID     string
    Generation int  // 第几代
}

// UserD的Ancestors = [
//   {UserC, 1},  // 直接推荐人
//   {UserB, 2},
//   {UserA, 3},
//   {UserRoot, 4}

// 2. 计算越级奖
func CalculateOverrideBonus(order Order) map[string]float64 {
    result := make(map[string]float64)
    
    // 获取下单用户的上级链路
    buyer := GetUser(order.UserID)
    
    for _, ancestor := range buyer.Ancestors {
        // 跳过第1代（那是推荐奖）
        if ancestor.Generation == 1 {
            continue
        }
        
        // 获取该上级的职级
        ancestorUser := GetUser(ancestor.UserID)
        maxGen := GetMaxGeneration(ancestorUser.Rank)

        rate := GetOverrideRate(ancestor.Generation, ancestorUser.Rank)
        bonus := order.Amount * rate
        
        result[ancestor.UserID] = bonus
    }
    
    return result
}
```

## 🏅 4. 平级奖（Peer Bonus）

### 📌 核心思想

平级奖是MLM系统中的**反压级机制**，设计理念非常巧妙：当你的下级达到与你相同的职级时，你不仅不会失去收益，反而会获得额外的平级奖励。这种设计从根本上解决了传统级差奖的一个致命缺陷——上级为了保持级差收益，故意不培养下级晋升的"压级"行为。

平级奖鼓励的是"培养出与自己同等级的伙伴"，体现了真正的团队协作精神。它传递的信息是：下级的成功就是你的成功，培养强者比控制弱者更有价值。

### 🎯 适用场景

- ✅ **传统直销企业**：安利、完美等老牌直销公司常用此机制防止压级
- ✅ **保险代理系统**：当下级成为经理时，上级经理获得团队管理的额外奖励
- ✅ **社交电商平台**：鼓励店主培养新店主，而不是把粉丝都留在自己手里
- ✅ **SaaS分销体系**：当下级代理商升级到同级时，奖励推荐人的培养成果
- ✅ **任何有职级体系的MLM系统**：只要存在级差奖，就应该配套平级奖

### 📐 计算公式

```
基础公式：
平级奖 = 订单金额 × 平级奖励比例

触发条件：
1. 下单人的某个上级 ancestor 与下单人 buyer 职级相同
2. ancestor.Rank == buyer.Rank
3. 触发 ancestor 获得平级奖

变种公式（团队业绩版）：
平级奖 = 平级下属的团队业绩 × 平级比例
```

**比例设置建议**：
- 普通会员 → VIP：平级奖 3%
- VIP → 经理：平级奖 5%
- 经理 → 总监：平级奖 7%
- 总监 → 合伙人：平级奖 10%

**关键规则**：
- 只有职级**完全相同**才触发，不是"接近"
- 可以向上触发多层（所有同级上级都拿）
- 通常不与级差奖冲突，而是叠加发放


### 📊 完整示例

**场景1：标准平级奖**
```
层级关系：
张三（总监）
  └─ 李四（总监）← 与张三同级
       └─ 王五（经理）
            └─ 赵六（VIP）

赵六下单1000元：
- 李四拿级差奖（总监比VIP高）
- 张三拿平级奖：1000 × 5% = 50元（因为李四也是总监）
```

**场景2：多层平级触发**
```
张三（总监）
  └─ 李四（总监）
       └─ 王五（总监）← 三个人都是总监
            └─ 赵六（经理）

赵六下单1000元：
- 王五：级差奖 + 其他奖励
- 李四：平级奖 50元（王五是总监）
- 张三：平级奖 50元（李四和王五都是总监）

三位总监因为"平级"都获得额外收益
```

**场景3：职级不同时无平级奖**
```
张三（合伙人）

       └─ 王五（经理）

王五下单1000元：
- 李四：获得正常奖励
- 张三：✗ 无平级奖（因为李四是总监，张三是合伙人）
```


### ⚠️ 常见陷阱

1. **比例设置过高导致成本失控**
   - ❌ 错误：平级奖10%，级差奖也10%，叠加后20%利润全没了
   - ✅ 正确：平级奖3-5%，确保总成本可控
   - 💡 建议：平级奖 + 级差奖 + 推荐奖 ≤ 毛利的70%

2. **忘记设置触发范围**
   - 问题：所有同级上级都拿，导致高层级人员拿太多
   - 解决：限制平级奖只向上追溯3-5代，或设置单笔上限

3. **与级差奖逻辑冲突**
   - 问题：系统认为"同级就没有级差"，结果既没级差也没平级
   - 解决：明确业务逻辑：同级时触发平级奖，不同级时走级差奖

4. **下级恶意晋升套利**
   - 问题：下级快速刷业绩晋升，让上级大量拿平级奖，然后分成
   - 解决：职级晋升设置冷静期、业绩真实性审核、防刷单机制

5. **统计口径不清晰**
   - 问题：平级奖是按单笔订单算，还是按月度团队业绩算？
   - 解决：在规则中明确写清楚，建议两种模式分开命名（平级奖 vs 平级管理奖）

### 💡 最佳实践

#### 设计原则

1. **比例递增原则**：职级越高，平级奖比例越高
   ```
   VIP平级奖：3%
   经理平级奖：5%
   总监平级奖：7%
   合伙人平级奖：10%
   
   → 越高级的培养越有价值，奖励也应该越丰厚
   ```

2. **限制深度原则**：不是所有同级上级都拿
   ```
   只追溯到第1个同级上级（直接上级）
   或
   追溯3代内的同级上级
   
   → 防止距离太远的人"躺赚"
   ```

3. **激励对象原则**：奖励给"培养者"而不是"旁观者"
   ```
   只有直接培养关系中的同级才触发
   跨部门、跨团队的同级不触发
   ```

4. **时效性原则**：可设置平级奖的有效期
   ```
   下级晋升到同级后，平级奖有效期12个月
   12个月后如果上级还未继续晋升，则平级奖减半或取消
   
   → 倒逼上级也要持续成长
   ```


#### 组合设计

**组合1：平级奖 + 级差奖**（最常见）

```
- 张三级差奖：0元（同级无级差）

```

```
- 平级奖：每笔订单触发，累计约5000元
- 团队管理奖：100000 × 3% = 3000元

双重激励，鼓励既培养人才又做大团队
```

**组合3：平级奖 + 育成奖**（一次性+持续性）
```

- 平级奖（持续性）：后续每笔订单都触发

先给大奖祝贺，再给持续激励
```

```go
// 1. 平级关系检测
func GetPeerRate(ancestor *User, buyer *User, rankConfig map[string]*RankConfig) float64 {
    // 检查职级是否相同
    if ancestor.Rank != buyer.Rank {
        return 0  // 职级不同，无平级奖
    }
    
    // 获取该职级的平级奖配置
    config, ok := rankConfig[ancestor.Rank]
    if !ok {
        return 0
    }
    
    return config.PeerRate
}

// 2. 平级奖计算（订单级）
func CalculatePeerBonus(order *Order, buyer *User, ancestors []*User) []BonusRecord {
    var records []BonusRecord
    
    for _, ancestor := range ancestors {
        // 只处理职级相同的上级
        if ancestor.Rank != buyer.Rank {
            continue
        }
        
        peerRate := GetPeerRate(ancestor, buyer, rankConfig)
        if peerRate <= 0 {
            continue
        }
        
        bonus := order.Amount * peerRate
        records = append(records, BonusRecord{
            UserID:    ancestor.ID,
            UserName:  ancestor.Name,
            BonusType: "平级奖",
            Amount:    Round(bonus),
            FromUser:  buyer.ID,
            Remark:    fmt.Sprintf("同为%s职级", ancestor.Rank),
        })
    }
    
    return records
}

// 3. 平级资格验证
func CheckPeerEligibility(sponsor *User, downline *User) bool {
    // 必须职级完全相同
    if sponsor.Rank != downline.Rank {
        return false
    }
    
    // 检查晋升时间（可选）
    monthsSince := MonthsSince(downline.LastPromotionDate)
    if monthsSince > 24 {
        return false  // 超过24个月，平级奖失效
    }
    
    // 检查活跃度（可选）
    if !sponsor.IsActive() {
        return false  // 上级不活跃，不享受平级奖
    }
    
    return true
}

// 4. 平级触发通知
func OnRankPromotion(user *User, newRank string) {
    // 当用户晋升时，检查其上级
    sponsor := GetSponsor(user.ID)
    if sponsor == nil {
        return
    }
    
    // 如果晋升后与上级同级，触发平级奖激活
    if sponsor.Rank == newRank {
        NotifyPeerBonusActivated(sponsor.ID, user.ID, newRank)
        
        // 记录平级关系开始时间
        RecordPeerRelationship(sponsor.ID, user.ID, time.Now())
    }
}
```

## 👔 5. 团队管理奖/领导奖（Leadership Bonus）

### 📌 核心思想

团队管理奖是对**团队规模和管理能力**的认可与奖励。不同于按单笔订单计算的实时奖励（如推荐奖、级差奖），团队管理奖通常是**周期性结算**（月结或周结），基于整个团队的累计业绩按职级比例发放。核心理念：**团队越大，管理越难，奖励越高**。

### 🎯 适用场景

- ✅ 大型直销组织（团队规模超过100人）
- ✅ 保险代理体系（区经理、总监管理多个团队）
- ✅ 社交电商平台（团长、店主管理分销网络）
- ✅ 教育培训机构（校区长管理多个班级/讲师）
- ✅ 任何强调"管理价值"的多层级组织

### 📐 计算公式

```
团队管理奖 = 团队总业绩 × 职级管理比例

关键定义：
- 团队总业绩：包含所有下级（所有代数）的订单总和
- 职级管理比例：根据职级不同，比例不同

典型比例：
- 经理：2%
- 总监：3%
- 合伙人：5%
- 董事：8%
```

### 📊 完整示例

**场景1：标准团队管理奖**
```
张三：总监（管理比例3%）
张三的团队结构：
- 直推10人
- 间接下级50人
- 本月团队总业绩：¥500,000

张三本月团队管理奖 = 500,000 × 3% = ¥15,000
```

```
  └─ 李四（总监3%）
       └─ 王五（经理2%）
            └─ ... 团队成员100人

本月总业绩：¥1,000,000

- 王五的团队业绩：¥200,000 → 管理奖 = ¥4,000
- 李四的团队业绩：¥600,000 → 管理奖 = ¥18,000
- 张三的团队业绩：¥1,000,000 → 管理奖 = ¥50,000

各级按各自团队业绩独立计算，不冲突
```

**场景3：职级晋升后的管理奖变化**
```

团队业绩：¥300,000
管理奖：¥6,000

李四 7月：晋升为总监（3%）
团队业绩：¥300,000
管理奖：¥9,000

同样的团队业绩，职级提升后管理奖增加50%
```

### ⚠️ 常见陷阱

1. **与其他奖励重复计算**
   - 问题：团队业绩既算了管理奖，又算了级差奖，双重发放
   - 解决：明确业务规则：管理奖独立计算，不与订单级奖励冲突

2. **团队业绩统计口径不清**
   - 问题：是否包含自己的业绩？是否包含同级下级的业绩？
   - 解决：明确定义（通常不含自己，含同级以下所有人）

3. **高层躺赚**
   - 问题：早期加入者团队大，每月躺拿高额管理奖
   - 解决：增加活跃度要求（如每月必须有直推业绩或团队培训）

4. **职级滑落后的处理**
   - 问题：用户职级下降，管理奖比例也下降，引起不满
   - 解决：设置保护期（降级后3个月内维持原比例）


### 💡 最佳实践

**设计原则**：职级越高比例越大，每级相差1-2%
**技术实现**：月初批量计算上月数据，避免实时计算压力
**组合设计**：与平级奖组合，既奖励团队大小，也奖励人才培养

```go
func CalculateLeadershipBonus(users map[string]*User, ranks map[string]*RankConfig) []BonusRecord {
    var records []BonusRecord
    for _, user := range users {
        rankConfig := ranks[user.Rank]
        if rankConfig == nil || rankConfig.LeadershipRate <= 0 {
            continue
        }
        
        teamVolume := CalculateTeamVolume(user.ID)
        bonus := teamVolume * rankConfig.LeadershipRate
        
        records = append(records, BonusRecord{
            UserID: user.ID,
            BonusType: "团队管理奖",
            Amount: Round(bonus),
            Remark: fmt.Sprintf("团队业绩%.0f × %.1f%%", teamVolume, rankConfig.LeadershipRate*100),
        })
    }
    return records
}
```

## 💰 6. 见点奖/见单奖（Point Bonus）

### 📌 核心思想

见点奖是最简单直接的奖励：**每产生一单，固定金额**。与订单金额无关，只与订单数量相关。核心理念：**多劳多得，积少成多**。特别适合高频低价产品，让分销员看到"每一单都有收益"的即时激励效果。

### 🎯 适用场景

- ✅ 快消品（日用品、零食、化妆品等高频复购）
- ✅ 低客单价产品（单价10-100元）
- ✅ 标准化产品（价格固定，无差异化）
- ✅ 需要冲量的场景（新品推广、活动促销）

### 📐 计算公式

```
见点奖 = 固定金额 × 订单数量

典型金额：
- 低价产品（<50元）：¥3-5/单
- 中价产品（50-200元）：¥5-10/单
- 高价产品（>200元）：¥10-20/单

发放层级：
- 第1代：¥10/单
- 第2代：¥5/单
- 第3代：¥3/单
- 第4-5代：¥2/单
```

### 📊 完整示例

**场景1：标准见点奖**
```
配置：每单¥5，向上发放5代

张三 → 李四 → 王五 → 赵六 → 钱七

钱七下单1次（订单金额不重要）：
- 赵六：¥5（第1代）
- 王五：¥5（第2代）
- 李四：¥5（第3代）
- 张三：¥5（第4代）

总计发放：¥20/单
```

**场景2：递减式见点奖**
```
张三 → 李四 → 王五 → 赵六

赵六下单：
- 王五：¥10（第1代，最高）
- 李四：¥6（第2代）
- 张三：¥3（第3代）

离得越近拿得越多
```

**场景3：月度累计**
```
张三团队本月产生200单：
- 第1代：50单 × ¥10 = ¥500
- 第2代：80单 × ¥6 = ¥480
- 第3代：70单 × ¥3 = ¥210

张三月度见点奖：¥1,190
```

### ⚠️ 常见陷阱

1. **金额设置过高**：每单¥20，100单就¥2000，成本失控
2. **代数过深**：发放到10代，每单成本累计过高
3. **刷单风险**：固定金额容易被刷单套利
4. **与推荐奖冲突**：两种奖励叠加，需要明确规则

### 💡 最佳实践

- 金额控制在产品毛利的5-10%
- 代数限制在3-5代
- 配合防刷单机制（同一用户连续下单限制）

### 🔧 技术实现要点

```go
func CalculatePointBonus(order *Order, ancestors []*User, pointAmount float64, maxGen int) []BonusRecord {
    var records []BonusRecord
    for i, ancestor := range ancestors {
        if i >= maxGen {
            break
        }
        records = append(records, BonusRecord{
            UserID: ancestor.ID,
            BonusType: "见点奖",
            Amount: pointAmount,
            Level: i + 1,
        })
    }
    return records
}
```

**某社交电商**：产品单价9.9元，见点奖¥2/单。用户月均推广50单，月入¥100。虽然单笔少，但参与门槛低，用户活跃度高。
