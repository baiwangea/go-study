快速开始

本示例位于 Asynq/，Redis 地址为 127.0.0.1:6379。启动 Redis 后，在模块目录执行：

Terminal
cd Asynq
go test ./...
go run main.go

示例会依次演示优先级队列、延迟任务、任务唯一约束、批量投递、订单超时取消和定时调度。

一、并发控制

Worker 的最大并发数由 asynq.Config.Concurrency 控制。一个 Worker 进程最多同时处理指定数量的任务。

main.go · Worker 配置
concurrency := 5

srv := asynq.NewServer(
    asynq.RedisClientOpt{Addr: redisAddr},
    asynq.Config{
        Concurrency: concurrency,
    },
)

当前示例使用：

main.go
concurrency := runtime.NumCPU() * 10

学习和调试时建议使用固定值，例如 5，更容易观察并发行为；生产环境应结合 CPU、IO 等待、下游限流和 Redis 吞吐量压测后确定。

队列权重

Queue priority
Queues: map[string]int{
    "critical": 6,
    "high":     3,
    "default":  2,
    "low":      1,
},

权重影响任务被选中的概率，不代表为每个队列固定分配并发数。上面的配置可理解为大致调度比例：

Scheduling ratio
critical : high : default : low = 6 : 3 : 2 : 1

如果需要不同队列拥有独立的并发额度，应启动多个 Worker 实例，分别监听不同队列。

二、任务进度

Asynq 负责任务排队和生命周期管理，不会自动生成业务百分比进度。当前示例通过日志表示开始和完成：

Handler logging
log.Printf("开始处理 - ID: %s", taskID)
// 执行业务逻辑
log.Printf("任务完成 - ID: %s", taskID)

对于包含多个步骤的长任务，应将进度写入 Redis 或数据库。例如使用以下 Redis key：

Redis key · JSON value
task:progress:{task_id}

{
  "status": "running",
  "progress": 60,
  "message": "正在检查支付状态"
}

接口层根据任务 ID 查询进度记录，即可向前端返回当前状态。

三、任务生命周期

Handler 返回值决定任务是否成功：

Handler 返回值任务结果后续行为
nil成功任务完成并从待处理队列移除
error失败按照重试策略重新执行
handler.go
func handler(ctx context.Context, task *asynq.Task) error {
    // 业务处理
    return nil
}

return fmt.Errorf("cancel order failed")

失败重试

Task options
client.Enqueue(
    task,
    asynq.MaxRetry(3),
)

任务不应该重试时，可以设置 asynq.MaxRetry(0)。重试逻辑应结合错误类型设计：网络抖动适合重试，参数错误通常不适合重试。

任务超时

Task timeout
client.Enqueue(
    task,
    asynq.Timeout(30*time.Second),
)

任务超时后，Handler 的 context 会被取消，任务按失败任务处理，并根据重试策略决定是否再次执行。

四、Worker 优雅退出

当前程序通过 srv.Run(mux) 阻塞运行。收到 SIGINT 或 SIGTERM 时，应停止调度器并关闭 Worker：

Graceful shutdown
go func() {
    sig := <-sigCh
    log.Printf("收到信号 %v，正在优雅关闭 Worker...", sig)

    scheduler.Shutdown()
    srv.Shutdown()
}()
方法行为适用场景
srv.Shutdown()停止接收新任务，等待正在执行的任务完成正常发布、扩缩容、服务退出
srv.Stop()立即停止，不等待当前任务完成紧急停止
scheduler.Shutdown()停止定时任务调度器服务退出前关闭 Scheduler
注意如果信号协程只打印日志而不调用 srv.Shutdown()，并不能真正完成优雅关闭。

五、任务结果

client.Enqueue 返回的是任务元信息，不是 Handler 的业务返回值：

Enqueue response
info, err := client.Enqueue(task)
fmt.Println(info.ID)
fmt.Println(info.Queue)

异步任务没有同步返回值。业务结果应由 Handler 写入数据库或 Redis，典型的订单取消流程如下：

订单取消 Handler
检查订单是否已支付
更新订单状态为 canceled
记录取消原因和完成时间
接口根据 order_id 查询订单状态

查询 Asynq 任务状态

可以使用 Inspector 查询任务的队列状态：

Inspector
inspector := asynq.NewInspector(
    asynq.RedisClientOpt{Addr: redisAddr},
)
defer inspector.Close()

info, err := inspector.GetTaskInfo(
    "low",
    "order:cancel:ORDER-20260803-1001",
)
if err != nil {
    log.Printf("查询任务失败: %v", err)
    return
}

log.Printf("状态: %s", info.State)
log.Printf("重试次数: %d", info.Retried)
log.Printf("最大重试次数: %d", info.MaxRetry)
状态说明
pending等待执行
active正在执行
scheduled延迟任务
retry等待重试
completed已完成
archived重试耗尽或已归档

六、并发安全

任务处理器运行在多个 goroutine 中，普通 map 不能安全地并发读写：

Unsafe in-memory state
var taskExecuted = make(map[string]bool)

单进程示例至少应该加锁：

sync.RWMutex
var (
    taskExecuted   = make(map[string]bool)
    taskExecutedMu sync.RWMutex
)

func isTaskExecuted(taskID string) bool {
    taskExecutedMu.RLock()
    defer taskExecutedMu.RUnlock()
    return taskExecuted[taskID]
}

func markTaskExecuted(taskID string) {
    taskExecutedMu.Lock()
    defer taskExecutedMu.Unlock()
    taskExecuted[taskID] = true
}
生产建议内存 map 只在单个进程内有效。多个 Worker 实例部署时，应使用 Redis SETNX 或数据库唯一索引实现分布式幂等。
